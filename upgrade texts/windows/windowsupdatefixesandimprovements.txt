## 1. Root cause: why streams don’t play

### 1.1 HLS detection is wrong for Xtream live `.ts` streams

From your manifest:

> **7.2 Stream Detection**  
> HLS path detection: URL contains `.m3u8` **OR `/live/` → use `hls.js`.**

Xtream live URLs usually look like:

```text
https://server.com/live/username/password/12345.ts
```

That contains `/live/` but **is not HLS**. It’s a raw MPEG-TS stream.

Your current logic is effectively:

```ts
const isHls = url.includes('.m3u8') || url.includes('/live/'); // BAD
if (isHls) {
  // use hls.js
} else {
  // native <video> or MPV
}
```

So:

- A `.ts` live stream with `/live/` is being forced into `hls.js`.
- `hls.js` cannot play a plain `.ts` stream → it errors out → nothing plays.

**Fix:** only treat `.m3u8` URLs as HLS. Remove the `/live/` condition.

In `src/components/VideoPlayer.tsx` (or wherever you detect):

```ts
// Before
const isHls = url.includes('.m3u8') || url.includes('/live/');

// After (correct)
const isHls = /\.m3u8($|\?)/i.test(url);
```

Then:

```ts
if (isHls && Hls.isSupported()) {
  // use hls.js
} else {
  // non-HLS: either native <video> or MPV
  video.src = url;
  video.load();
  video.play().catch(err => {
    // surface error to UI
  });
}
```

This alone is enough to make **.ts live streams actually attempt playback instead of dying in hls.js**.

### 1.2 `liveFormat='auto'` needs to pick `.ts` vs `.m3u8` correctly

Your manifest says:

> `liveFormat: 'auto'` → renderer selects `.m3u8` by default for `auto` to improve compatibility.  
> Note: `xtreamApi.getLiveStreamUrl()` will return `.ts` when called without an explicit format; the renderer intentionally overrides this when starting playback.

Right now that means:

- Many servers that only expose `.ts` will still get `.m3u8` URLs → 404 or immediate failure.
- Combined with bad HLS detection, nothing plays.

You need **central, robust selection** instead of “renderer tries to override”.

In `src/services/xtreamApi.ts`, add this helper:

```ts
// src/services/xtreamApi.ts

import type { AppSettings } from '@/types/settings';
import type { XtreamProfile } from '@/types/xtream';

function selectLiveFormat(
  profile: XtreamProfile,
  settings: AppSettings,
): 'ts' | 'm3u8' {
  if (settings.liveFormat === 'ts' || settings.liveFormat === 'm3u8') {
    return settings.liveFormat;
  }

  const allowed = profile.auth?.server_info?.allowed_output_formats ?? [];
  const lowered = allowed.map(f => f.toLowerCase());

  // Xtream panels usually list things like: ["ts","m3u8","hls"]
  if (lowered.some(f => f.includes('m3u8') || f.includes('hls'))) {
    return 'm3u8';
  }

  return 'ts';
}

export function getLiveStreamUrl(
  profile: XtreamProfile,
  settings: AppSettings,
  streamId: number,
) {
  const format = selectLiveFormat(profile, settings);
  const { serverUrl, username, password } = profile;

  if (format === 'm3u8') {
    return `${serverUrl}/live/${username}/${password}/${streamId}.m3u8`;
  }
  return `${serverUrl}/live/${username}/${password}/${streamId}.ts`;
}
```

Then in your **play-channel handler** (likely in `App.tsx` or `LivePage.tsx`):

```ts
import { getLiveStreamUrl } from '@/services/xtreamApi';
import { useSettings } from '@/hooks/useSettings';

const { settings } = useSettings();

function handlePlayChannel(ch: XtreamChannel) {
  const profile = activeProfile!;
  const url = getLiveStreamUrl(profile, settings, ch.stream_id);

  setStreamUrl(url);
  setStreamType('live');
  setActiveChannel(ch);
}
```

Key points:

- `liveFormat: 'auto'` is now **actually “auto”**: it uses the server’s `allowed_output_formats` to decide.
- No more “renderer secretly forcing `.m3u8`” – you have a single source of truth.

## 2. MPV integration: wiring it so it can’t block playback

Your manifest’s **7.10 MPV Integration** describes an MPV stack, but:

- `electron/main.cjs`’s IPC handlers (3.8) do **not** list any `mpv:*` channels.
- `electron/preload.cjs`’s whitelists (4.1, 4.2) also have **no `mpv:*` channels**.

So if your renderer / `useMpv` hook ever calls:

```ts
window.electronAPI.invoke('mpv:load-live', {...})
```

you’ll hit one of these:

- Preload blocks the channel → promise rejects → playback logic never continues.
- Main doesn’t have an `ipcMain.handle('mpv:load-live')` → same result.

Depending on how you coded the front-end, that can mean: **“nothing ever starts playing”**, even if HLS would have worked.

### 2.1 Minimum wiring to not break playback

If you **haven’t actually created `mpvManager.cjs` yet** but already added `useMpv` calls in React, you have two options:

1. **Disable MPV on the renderer side for now** and always use `VideoPlayer` (HLS/native) until MPV is fully wired.
2. Or **actually wire the IPC channels** so MPV can be used safely and fallback to HLS on error.

If you want the second (better) option, do the following.

#### (A) Add IPC handlers for MPV in `electron/main.cjs`

At the top:

```js
const { MpvManager } = require('./mpvManager.cjs');
let mpvManager;
```

After creating your `BrowserWindow` (`win`), when it’s ready:

```js
win.once('ready-to-show', async () => {
  win.show();
  try {
    mpvManager = new MpvManager();
    await mpvManager.initialize(win, appSettings); // pass initial settings
  } catch (err) {
    console.error('[MPV] Failed to initialize:', err);

```

Then extend your IPC handlers:

### 2.2 Make sure HLS still works even if MPV is broken

To avoid a situation where one broken engine kills everything:

- Keep a **single entry** component that decides engine at runtime, e.g. `VideoPlayerEngine`:

```tsx
// pseudo
if (!mpvAvailable) {
  return <VideoPlayer /* HLS/native only */ ... />;
}
// if URL is .ts, prefer MPV; if .m3u8, you can choose MPV or HLS
```

- In your MPV hook (`useMpv`), if you get `mpv:unavailable` on startup, set `mpvAvailable=false` and have the engine fall back to HLS.

That way:

- If MPV binary is missing / misconfigured, you **still have working playback** with HLS/native.
- MPV becomes an enhancement, not a single point of failure.

Even if you don’t fully wire `VideoPlayerEngine` right now, at minimum: **don’t replace the existing HLS `VideoPlayer` until MPV is confirmed working.** That’s the easiest way to restore basic playback.

### 4.2 `liveBufferPreset` not actually affecting HLS

The manifest says:

> `liveBufferPreset` exists and is hooked to MPV profiles, but HLS `maxBufferLength` values are hardcoded.

If you **still use HLS.js** for some streams, wire it properly:

### 4.3 `useStreamHealth` should unsubscribe cleanly

You poll the `<video>` every 1000ms. Make sure you clear the interval on unmount or when switching engines (HLS → MPV or vice versa), otherwise you can end up with “ghost” intervals referencing a stale video element.

```ts
useEffect(() => {
  if (!videoRef.current) return;

  const id = window.setInterval(() => {
    // collect metrics
  }, 1000);

  return () => {
    window.clearInterval(id);
  };
}, [videoRef.current, engineType]); // engineType = 'hls' | 'native' | 'mpv'
```

### 4.4 Clarify `streamType` for MPV

Your global state:

```ts
const [streamType, setStreamType] = useState<'live' | 'vod'>();
```

Make sure when you call MPV you pass consistent types (`'live'` | `'vod'`) and don’t accidentally introduce `'series'` or other values; otherwise your reconnection / keyboard shortcuts which branch on `streamType` might misbehave.

E.g.:

```ts

setStreamType('vod');
```
